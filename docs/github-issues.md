# GitHub issue skill maintenance

Nexa uses `github/awesome-copilot`'s `github-issues` skill at project scope.
The complete upstream skill lives in `.agents/skills/github-issues/`; keep that
directory unchanged, including whitespace. Repository policy is in
[`AGENTS.md`](../AGENTS.md#github-issues), and the bug, feature, and task templates
are in [`.github/ISSUE_TEMPLATE/`](../.github/ISSUE_TEMPLATE/).

## Provenance

[`skills-lock.json`](../skills-lock.json)'s `github-issues` entry records the source,
full upstream commit in `ref`, original `skillPath`, and computed folder hash.
The entry is generated by the existing [Skills CLI](https://github.com/vercel-labs/skills).
The reviewed installation uses `skills@1.5.26`; the commands below pin that tool
version so its source and update behavior are reproducible.

The upstream MIT copyright and permission notice is preserved verbatim in
[`.agents/licenses/github-awesome-copilot-LICENSE`](../.agents/licenses/github-awesome-copilot-LICENSE).
`prek.toml` excludes vendored skills and licenses from whitespace, line-ending,
BOM, and final-newline fixers, including this skill and its external license.
Biome also excludes vendored skill and license files to preserve upstream example
code. Repository-owned files and the other vendor checks remain enabled. The reviewed upstream
skill contains trailing whitespace, and its license lacks a final newline.

## Refresh or update only this skill

Start from a clean project checkout, with the tools in `mise.toml` installed.
Run commands at the project root. Do not use `--global` or `--all`.

Use this explicit `add` command to refresh only the selected skill and its
metadata in place. The locked `ref` selects the recorded commit; to upgrade,
replace it with a newly reviewed full commit before running the installer:

```bash
issue_skill_ref=$(mise exec -- bun -p 'require("./skills-lock.json").skills["github-issues"].ref')
# For an upgrade, set issue_skill_ref to the full upstream commit you reviewed.
mise exec -- bunx skills@1.5.26 add \
  "https://github.com/github/awesome-copilot/tree/${issue_skill_ref}/skills/github-issues" \
  --skill github-issues --agent codex --yes
```

Keep `--agent codex`: it selects the shared `.agents/skills/` project location.
In this CLI version, even a named `skills update --project` cannot pin the target
agent and may create additional agent directories based on the maintainer's
environment. The explicit command above works both inside and outside Codex.

Before adopting a revision, review the entire skill and bundled references against
the recorded version. In particular, check repository-template precedence, tool
requirements, labels/types, and invocation behavior (the current description
triggers issue work automatically and mentions MCP). Nexa explicitly uses its
repository templates first and authenticated `gh` for both reads and writes;
an MCP connection is optional. Review changes to upstream licensing as well.

After installation, compare the installed file list and bytes with
`skills/github-issues/` at the locked upstream commit, and verify the lock entry's
hash. Refresh the external license from that same commit if it changed. Review
the diff: only this skill, its lock entry, and any necessary attribution or
maintenance notes should change. `AGENTS.md`, repository templates, and other
skills must remain unchanged by the installer. Run `task verify` and the hooks,
then repeat the byte comparison to catch accidental formatting.

## CLI use in a clone

Use the existing authenticated `gh` version pinned in `mise.toml`. Resolve the
destination from the current checkout and verify it matches the intended Git
remote before any write; account for `GH_REPO` or a configured `gh` default that
could override that context. For example:

```bash
git remote -v
mise exec -- gh repo view --json nameWithOwner --jq .nameWithOwner
```

Use that verified repository explicitly with `--repo` or in `gh api` paths.
`gh issue list --state all --search 'search terms'` covers open and closed issues;
read plausible matches with `gh issue view` before creating anything. When
composing a body from a repository Markdown template, omit its YAML frontmatter.
Use a body file with `gh issue create/edit --body-file` or a JSON file with
`gh api --input` to preserve multiline text.

The pinned `gh issue create/edit` commands do not accept `--type`; use `gh api`
when actual repository types or native relationships require it. Consult the
relevant bundled reference and current API behavior instead of copying example
repository names or assuming labels/types exist. Read back requested changes,
including native parent/sub-issue or blocking relationships. A body link alone
does not verify those relationships.

The [draft exercises](validation/github-issues.md) cover template selection,
uncertainty, and preservation of existing content. The implementation PR records
the temporary-checkout refresh and live read-only clone checks separately from
those drafts; no throwaway issues are needed.

## Scheduled candidate preparation

The [project skill updater](skill-updates.md) preserves this contract. It reports
new `github-issues` candidates without installing them until an upstream and
license review is recorded in `.github/skills-review.json` and merged. The updater
checks that approved full revision and its hashes before installation, synchronizes
external attribution, and repeats the file-list, byte, and hash comparisons after
`task verify` and `task hooks:run`. Candidate detection alone is never approval.
